# Security policy

Himitsu's main promise is privacy, so security reports are very welcome. Thank you for helping keep its users safe.

## Supported versions

Only the latest release receives security fixes. Please check that the problem still happens on the latest release, or on the `main` branch, before reporting.

| Version | Supported |
|---|---|
| Latest release | Yes |
| Older releases | No |
| Debug builds (`dev.bianperdev.himitsu.dev`) | Report anyway if the problem also affects `main` |

## Reporting a vulnerability

**Do not open a public issue for a vulnerability.**

Report it privately through GitHub: open the repository's **Security** tab and choose **Report a vulnerability** (GitHub private vulnerability reporting). Only the maintainers can see the report, and we can discuss and fix it in a private security advisory before anything is published.

Please include:

- the Himitsu version and channel (F-Droid, GitHub Releases, Google Play or your own build), the Android version and the kind of device (a generic description is enough);
- the steps to reproduce, and what an attacker needs (physical access to an unlocked or locked phone, another app on the device, a position on the network, a malicious character card or model file...);
- the impact as you understand it.

**Never include real API keys, passwords, private chats or personal data** in a report, a proof of concept or a log. Use fake keys and invented test content. If a log is needed, redact it first.

We aim to acknowledge reports within 7 days. Himitsu is maintained by volunteers, so fixes may take longer; we will keep you informed and credit you in the advisory unless you prefer otherwise. Please give us a reasonable time to release a fix before disclosing the issue publicly.

## Scope

Especially interesting:

- **Encryption at rest:** reading chats, characters, API keys, images or sealed preferences without the device's Keystore key or the recovery code; weaknesses in key derivation, wrapping or the sealed file format.
- **App lock:** any way to see or use content without authenticating, including through dialogs, recents, notifications, the clipboard, intents or other exported components.
- **Disguise bypass:** any path from a decoy (calculator, compass, unit converter) to Himitsu's content that skips authentication, or a way to recover the secret code. Note that the disguise's documented limits (Settings › Apps, the package name, store history, the system prompt label, some notification headers, adb) are known and not vulnerabilities; see [PRIVACY.md](PRIVACY.md#what-the-disguise-cannot-hide).
- **Data leaving the device:** any network connection other than the AI endpoint the user configured or a model download the user started; credentials sent to another host; user content written to Logcat, backups or shared storage.
- **Untrusted input:** crashes or worse caused by imported character cards, lorebooks, Regex scripts, chat archives, GGUF model files or their chat templates.

Out of scope:

- Attacks that need a rooted or compromised device, or an unlocked phone together with the user's credential.
- What third-party AI providers do with the requests the user sends them.
- Content generated by a model.
- Vulnerabilities in dependencies that Himitsu cannot reach; please report those upstream (still tell us if Himitsu is affected).
